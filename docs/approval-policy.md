# 승인 정책

에이전트는 구현하고, 사람은 위험이 큰 변경만 직접 본다.

## 기본 원칙

1. 모든 변경은 기능 브랜치와 PR로 한다. `main`에 직접 푸시하지 않는다.
2. 승인자는 대표 한 명이다. 에이전트는 자기 PR을 승인하지 못한다.
3. 등급이 불확실하면 한 단계 위로 올린다.
4. "완료"의 기준은 에이전트의 보고가 아니라 PR diff와 CI 결과다.
5. 이 문서를 바꾸는 변경은 3등급이다.

## 등급

| 등급 | 해당하는 변경 | 머지 조건 |
| --- | --- | --- |
| 1 | 문구, 스타일, 반응형, 테스트 추가, 읽기 전용 화면, 문서 | CI 통과 (확대 일정 참고) |
| 2 | 인증과 무관한 새 기능, 화면 흐름 변경, 내부 API, 의존성 추가 | CI 통과 + 대표가 PR 설명, 테스트 결과, 프리뷰 화면을 확인 |
| 3 | 아래 3등급 목록에 해당하는 모든 변경 | CI 통과 + 대표가 diff를 직접 읽거나 그 변경 전용 테스트를 확인 |

## 3등급 목록

다음 중 하나라도 건드리면 3등급이다. (2026-10-16 기준 실제 경로로 확인함)

- DB 스키마와 마이그레이션: `prisma/schema.prisma`, `prisma/migrations/**`
- 인증과 권한: `middleware.ts`, `lib/auth.ts`, 그리고 `app/api/**/route.ts` 각각의 세션·level·`isSuperAdmin` 검사 로직 (라우트별로 인라인되어 있고 공용 헬퍼로 묶여 있지 않음 — 건드리는 라우트 단위로 3등급)
- 이메일과 푸시 발송 코드, 발송 스위치 설정: `lib/email.ts`, `lib/message-action.ts`, `lib/message-text.tsx` (주의: `EMAIL_MODE` 스위치는 이 레포에 아직 구현되어 있지 않음 — 새로 추가하는 코드 자체가 3등급 대상)
- 개인정보의 조회·저장·전달과 채팅/대화방 접근 규칙: `app/(route)/account/(auth)/messages/**`, `components/chat/**`, `components/chatbot/**`, `components/dashboard/concierge-message-widget.tsx`, `app/api/chatbot/**`, `lib/chatbot/**`
- AI 호출 구조 — 프롬프트, 레드라인, 모델 이름, 비용 상한: `lib/chatbot/handle-message.ts`(시스템 프롬프트·모델명), `lib/chatbot/search-units-tool.ts`, `lib/ai-search/**`, `app/api/ai/extract-listing/route.ts`, `app/api/ai-search/route.ts`
- 환경변수, 배포 설정, CI 설정: `.github/workflows/deploy.yml`, `next.config.mjs`, `middleware.ts` (이 레포에는 `vercel.json` 없음 — 생기면 바로 3등급 목록에 추가)
- 납부 승인과 계약 생성 로직: `app/api/pms/payments/[id]/verify/route.ts`, `app/api/pms/payments/[id]/route.ts`, `app/api/pms/leases/route.ts`, `app/api/pms/leases/[id]/route.ts`, `app/api/cron/expire-leases/route.ts`, `lib/landlord/get-landlord-payments.ts`, `lib/tenant/get-tenant-payment-history.ts`, `lib/staff/get-pending-payment-verifications.ts`
- admin-rbs-homes 저장소의 모든 변경 (별도 GitHub 저장소 — 이 레포의 하위 경로 아님)
- 이 문서 (`docs/approval-policy.md`)

새 디렉토리나 파일이 생겨서 위 범주에 해당하게 되면, 그 변경을 담은 PR 안에서 이 목록도 같이 갱신한다.

## 에이전트가 하면 안 되는 것 (모든 등급)

- 운영 DB에 접속하거나 수정하는 것. 개발은 로컬 DB만 쓴다.
- `.env` 파일을 읽거나 수정하거나 출력하는 것. 비밀값을 로그나 PR에 남기는 것.
- 운영 서버나 운영 환경에 배포하거나 마이그레이션을 실행하는 것.
- `main`에 직접 푸시하는 것. 보호 설정을 끄는 것.
- 테스트를 삭제하거나 건너뛰도록 바꿔서 통과시키는 것.
- 브리프에 없는 파일이나 기능을 고치는 것.
- 실제 사용자에게 이메일이나 푸시를 보내는 것. 발송 스위치가 `live`가 아닌 환경에서도 같다.
- 사용자 개인정보를 출력하거나 외부로 보내는 것.
- 새 의존성을 이유 없이 추가하는 것. 추가하면 PR 설명에 이유를 쓴다.

## 머지 전 필수 검사 (CI)

CI는 깨끗한 체크아웃에서 실행한다. 로컬 캐시나 커밋하지 않은 파일에 의존하지 않기 위해서다.

1. 빌드 (`npm run build`)
2. 타입체크 (`tsc --noEmit`)
3. 린트
4. 단위 테스트와 핵심 흐름 테스트
5. 인증이 필요한 API 라우트가 세션을 확인하는지 검사
6. 빈 MySQL에 마이그레이션을 적용해 보는 검사 (스키마 변경이 있을 때)

다른 모델이 하는 자동 리뷰는 보조로만 쓴다. 3등급의 대체물이 아니다.

## 핵심 흐름 (확정 전 초안)

PR이 깨뜨리면 안 되는 흐름이다. 대표가 확인하고 고친다.

1. 로그인과 역할별 접근 분리
2. 매물 공개 조회와 검색 (숨김, 계약됨 제외)
3. 매물 등록 (AI 등록 포함)과 수정
4. 문의와 투어 요청 접수, 승인
5. 케어 요청 전체 흐름
6. 납부 영수증과 직원 승인
7. 계약 업로드로 계약 생성과 매물 숨김
8. 카카오 검색 응답
9. 확인 요청의 중복 발송 방지
10. 임차인 정보가 외부 브로커에게 나가지 않는 규칙

## 발송 스위치

환경변수 `EMAIL_MODE` 하나로 발송을 통제한다.

| 값 | 동작 | 사용하는 환경 |
| --- | --- | --- |
| `off` | 발송하지 않고 로그만 남긴다. | 로컬 개발, CI, EC2 |
| `redirect` | 모든 메일을 지정한 개발자 주소로만 보낸다. | 프리뷰, 발송 테스트 |
| `live` | 실제 수신자에게 보낸다. | 운영(Production)만 |

운영에서 `live`로 켜는 결정은 대표가 한다. 값이 없거나 알 수 없으면 `off`로 동작한다.

## 배포와 롤백

- 운영 배포는 PR이 머지된 뒤에만 한다. 릴리스마다 태그를 붙인다 (`release-YYYYMMDD-N`).
- 되돌릴 때는 직전 태그로 재배포한다.
- DB 마이그레이션은 기존 데이터에 영향 없는 추가 변경을 원칙으로 한다. 컬럼 삭제와 타입 변경은 따로 승인한다.
- 마이그레이션 배포 전에 DB 백업이 있는지 확인한다.

## 반려 기록

반려하거나 보완을 요청할 때 브리프의 11번에 한 줄 사유와 태그를 남긴다.
태그는 범위 이탈, 테스트 부족, 보안, 정책 위반, 품질, 기타 중에서 고른다.

## 확대 일정 (제안)

신뢰는 단계적으로 넓힌다.

| 시기 | 1등급 | 2등급 | 3등급 |
| --- | --- | --- | --- |
| 시작 후 2주 | PR 요약을 확인한 뒤 머지 | 요약과 프리뷰 확인 | 직접 검토 |
| CI와 핵심 흐름 테스트가 안정된 뒤 | 자동 머지 | 요약과 프리뷰 확인 | 직접 검토 |

"안정"의 기준은 대표가 정한다. 예: 핵심 흐름 테스트 10개가 모두 있고 2주 동안 머지 후 되돌림이 0건.
