### 사고 기록 (2026-11-12)

- **무슨 일**: 이 작업(B-20261111-03) 중 로컬 검증을 위해 `npm run build`를 돌렸다(B-20261111-02 작업 중 1회, B-20261111-03 작업 중 1회, 총 2회). 두 번 모두 `.env.local`의 `DATABASE_URL`이 로컬이 아니라 실제 운영 Railway 호스트를 가리키고 있는 상태였다. `npm run build`(`prisma generate && next build`)는 가드를 거치지 않는 명령이라서 그대로 실행됐고, `next build`의 사이트맵 생성 단계(`app/sitemap.xml`)가 **실제 운영 DB에 읽기 전용으로 연결해서 매물 목록을 조회했다**(빌드 로그에 "매물 페이지: 1416개"로 실측 — 가짜 숫자가 아니라 실제 운영 매물 수). 쓰기 쿼리는 없었고 비밀값을 로그나 출력에 남기지도 않았지만, "운영 DB 접속·조회 금지" 규칙을 어겼다.
- **원인**: 이 브리프(B-20261111-03)의 가드 설계가 "`db:local:*`, `dev:local`만 가드를 걸고 `build`/`test`/`lint`에는 걸지 않는다"였다. CI에서는 이 세 명령이 항상 가짜 `DATABASE_URL`(`.github/workflows/ci.yml`의 job-level env)로 실행되니 안전하지만, **로컬에서 `npm run build`를 직접 돌리면 CI의 가짜 값이 없어서 `.env.local`의 실제 값이 그대로 쓰인다**는 점을 설계 당시 충분히 고려하지 못했다.
- **조치**: 가드를 거치는 별도의 `build:local` 스크립트(`scripts/with-local-db.js` → `scripts/build-local.js` → `prisma generate` + `next build`)를 추가했다. `npm run build` 자체는 바꾸지 않았다(Vercel/EC2/CI가 그대로 사용하므로). `CLAUDE.md`에 "로컬 검증은 `build:local`/`dev:local`만 쓰고, 로컬에서 `npm run build`/`npm run dev`를 실행하지 않는다"는 규칙을 추가했다. 이후 로컬 빌드 검증은 전부 `npm run build:local`로 진행한다.

### AC-1 방식 변경과 남은 문제 (2026-11-12)

- **account 테이블 CREATE 이력이 마이그레이션에 없어 빈 DB에서 전체 재현이 불가능하다.** `prisma/migrations/` 전체를 검색해도 `account` 테이블을 만드는 마이그레이션이 없는데, `20250826071318_` 마이그레이션은 그 테이블이 이미 있다고 가정하고 `ALTER TABLE account DROP FOREIGN KEY ...`로 시작한다. 빈 로컬 MySQL에 `prisma migrate deploy`를 순서대로 적용하면 13번째 마이그레이션까지는 성공하고 14번째(`20250826071318_`)에서 `Error: P3018` / `Database error code: 1146` / `Table 'rbs_local.account' doesn't exist`로 실패한다. `account` 테이블(NextAuth용으로 추정)이 과거에 마이그레이션 바깥(수동 SQL 또는 `db push`)으로 운영 DB에 만들어졌고 그 생성 기록이 레포에 없는 것으로 보인다. **이 간극을 메우는 작업(베이스라인 마이그레이션 보강 등)은 운영 마이그레이션 이력과 직접 연결되는 문제라 별도 브리프가 필요하고, 이번 브리프에서는 하지 않는다.**
- 그래서 이번 브리프는 `db:local:migrate`(`prisma migrate deploy`) 대신 `db:local:schema`(`prisma db push --skip-generate`)로 AC-1을 재정의했다. `db push`는 마이그레이션 기록이 아니라 현재 `schema.prisma`를 기준으로 테이블을 만들기 때문에 이 간극의 영향을 받지 않는다. `prisma/migrations/` 폴더는 이 과정에서 전혀 수정하지 않았다.
- **CI의 "빈 MySQL에 마이그레이션을 적용해 보는 검사"(`docs/approval-policy.md`의 머지 전 필수 검사 6번, 스키마 변경이 있을 때)는 같은 이유로 보류한다.** 그 검사를 `migrate deploy` 기준으로 그대로 추가하면 이 간극 때문에 항상 실패하므로, 베이스라인 마이그레이션 문제가 해결되기 전까지는 추가하지 않는다.

### 사전 조사 결과 (읽기 전용, 코드/설정 수정 없음, `.env*` 내용은 읽지 않음)

**1. 운영 MySQL 주 버전**

- **확인 불가.** `prisma/schema.prisma:5-8`의 datasource는 `provider = "mysql"`뿐이고 버전을 못 박지 않음. 저장소 안에 Railway MySQL 버전을 적어둔 파일이 없음(`CLAUDE.md`, `docs/approval-policy.md` 등 전부 "Railway MySQL"이라고만 언급). Railway 콘솔/대시보드를 직접 조회하면 알 수 있지만 이는 "운영 DB 접속과 조회"(범위 밖)에 해당해서 하지 않았다.
- 브리프 지시대로 **`mysql:8.0`을 제안**한다. Prisma 5.19용 커넥터가 MySQL 8.0을 공식 지원하고, Railway가 신규 MySQL 플러그인 생성 시 기본값으로 8.0 계열을 쓰는 것으로 알려져 있어 실제 운영과 어긋날 위험이 비교적 적다. (추측 표시: 이 문단의 "Railway 기본값" 부분은 운영 환경을 직접 확인하지 않은 일반 지식이다.)

**2. package.json scripts / prisma 설정 / 기존 seed 유무**

- `package.json` scripts(관련 부분): `"dev": "prisma generate && next build"`, `"build": "prisma generate && next build"`, `"start": "next start"`, `"lint": "next lint"`, `"seed": "node prisma/seed.js"`, `"test": "vitest run"`.
  - **`dev` 스크립트가 실제로는 `next dev`가 아니라 `next build`를 돈다.** 기존 버그로 보인다(이번 브리프 범위 밖이라 고치지 않음, 그대로 보고만 함). 그래서 `dev:local`은 이 `dev` 스크립트를 재사용하지 않고 `next dev`를 직접 호출하도록 새로 만들 계획이다.
  - `package.json`에 `"prisma": { "seed": ... }` 설정 블록이 **없다** → `prisma migrate reset`/`prisma db seed` 자동 시드 훅이 걸려 있지 않음. 즉 지금은 시드가 완전히 수동이다.
- `prisma/seed.js` (기존): `new PrismaClient()`로 직접 연결해서 **`prisma.unit.deleteMany()`로 전체 Unit을 지우고** 가짜 5,000건을 새로 넣는 스크립트. **호스트 가드가 전혀 없다.** 현재 `DATABASE_URL`을 로컬이 아니라 다른 값(예: 운영 Railway)으로 잘못 설정한 채 `npm run seed`를 실행하면 운영 Unit 테이블 전체가 삭제될 수 있는 **기존의 위험한 스크립트**다. 이번 브리프의 "가짜 데이터만" 시드(`prisma/seed-local.js` 신설 예정)는 이것과는 별도 파일로 만들고, 기존 `prisma/seed.js`/`seed.js` npm script는 건드리지 않는다(앱 코드/기존 스크립트 변경은 범위 밖) — 다만 이 위험을 10번 "미해결"에 기록해 둔다.
- `prisma/seed-test-users.js` (기존): `buyer@test.com`/`seller@test.com` 2계정만 만드는 별도 스크립트, 존재 시 skip(멱등적)이지만 이 역시 가드 없음. npm script로 등록돼 있지 않음(직접 `node` 실행 전용).

**3. `.env`/`.env.local` 읽기 우선순위 (prisma CLI vs `next dev`)**

- `.env*` 글롭 확인(이름만, 내용은 읽지 않음): 저장소 루트에 **`.env.local`과 `.env.example`만 존재, 루트 `.env`는 없음.** `prisma/.env`도 없음.
- `.gitignore:28-30`에 `.env*.local`과 `.env`가 이미 등록돼 있어 `.env.local`은 git 추적 대상이 아님(`git ls-files`로 확인, `.env.example`만 추적됨) — **AC-7의 "git 추적 안 됨" 조건은 이미 만족**하고 있다.
- `next dev`/`next build`: Next.js가 자체적으로 `.env.local`을 자동으로 읽어 `process.env`에 올린다(표준 Next 동작, 우선순위 `.env.$(NODE_ENV).local` > `.env.local` > `.env.$(NODE_ENV)` > `.env`). 그래서 `dev:local`에 한해서는 별도 로딩 코드 없이 `next dev`만 실행해도 `.env.local`의 `DATABASE_URL`을 읽는다.
- **prisma CLI(`migrate`, `db push`, `studio` 등)는 `.env.local`을 자동으로 읽지 않는다.** prisma CLI는 `prisma/.env` 또는 루트 `.env`만 자동 로드 대상으로 본다. 지금 저장소에는 둘 다 없으므로, **현재 상태에서 `npx prisma migrate deploy`를 그냥 실행하면 `DATABASE_URL` 환경변수 자체가 비어 있어서 즉시 에러로 멈춘다**(실측: 이 세션에서 `DATABASE_URL`이 쉘에 없는 상태로 `npx prisma generate`는 성공했지만 — `generate`는 연결이 필요 없어서 통과한 것이고, `migrate`/`db push`류는 연결이 필요해서 통과하지 못한다).
- **가드를 어디에 걸지(해결 방향)**: npm script 레벨에서 바로 `prisma`/`next`를 부르지 않고, 공용 Node 래퍼 스크립트(`scripts/with-local-db.js`)를 하나 거치게 한다. 이 래퍼가 (a) `process.loadEnvFile('.env.local')`로 **`.env.local`만** 명시적으로 로드하고(루트 `.env`는 아예 참조하지 않음), (b) 로드된 `DATABASE_URL`의 호스트를 가드 함수로 검사하고, (c) 통과하면 그제서야 실제 명령(`npx prisma migrate deploy`, `next dev`, `docker compose up -d` 등)을 **같은 프로세스 환경을 물려서** 자식 프로세스로 실행한다. 가드 판정 로직 자체는 순수 함수(`scripts/guard-local-db.js`가 export하는 `isAllowedLocalHost(databaseUrl)` 같은 형태)로 분리해서 파일 I/O 없이 vitest로 바로 테스트한다(AC-5).

**4. 빈 MySQL에 마이그레이션 적용 시험**

- **미확인.** `docker version`/`docker ps` 모두 `failed to connect to the docker API at npipe:////./pipe/dockerDesktopLinuxEngine ... The system cannot find the file specified.` — Docker Desktop 데몬이 떠 있지 않음. 이전 브리프(B-20261111-01-ci)에서도 같은 상황이었다.
- 지시대로 **Docker를 직접 띄우려 하지 않았고, `db push`로 우회하지도 않았다.** Docker Desktop을 켠 뒤 재시도가 필요하다.

**5. 시드에 필요한 필수 필드/상태값**

- `User` (`prisma/schema.prisma:10-`): `level`은 스키마 주석에 의미가 이미 적혀 있음 — 0 관리자, 1 일반유저, 2 에이전트, 3 브로커, 4 오너, 5 세입자, 20 프리세일 에이전트, 30 프리세일 브로커, 40 프리세일 오너. 브리프가 요구하는 "0, 1, 2 또는 3, 20 또는 30"과 그대로 대응됨. `status`는 -1 정상/0 정지/1 탈퇴(기본 -1). `password`는 nullable(bcrypt 해시 저장).
- `Unit` (`:233-`): `adminId`(Int, 필수, User 참조 — FK 관계는 없고 평범한 Int), `agentId`(Int?, nullable — 에이전트 배정용), `title`/`type`/`sellType`/`ownerName`/`area` 필수. **`status` 의미(주석 원문)**: `Ongoing = 0, Completed = 1, Contracted = 2, UnderNegotiation = 3`. 공개 매물 목록 기본 필터는 `lib/action.ts:22` `DEFAULT_STATUS = [0, 1, 3]`(주석은 "0과 3만"이라고 돼 있지만 실제 배열엔 1도 포함돼 있어 주석과 코드가 불일치 — 기존 버그, 이번 범위 밖, 기록만). 이 Unit 모델에는 "공개/숨김"을 구분하는 별도 필드가 없고, **계약 생성 시 `status`를 2로 바꾸는 것 자체가 "숨김" 역할**을 한다(`app/api/contract-draft/[id]/upload/route.ts:158-161`에서 계약 완료 시 `status: 2`로 갱신 → `DEFAULT_STATUS`에 2가 없어서 기본 목록에서 빠짐). 즉 브리프가 말한 "공개/숨김/계약됨" 3상태는 이 코드베이스에서는 **"공개(0 또는 3, 그리고 1도 포함됨) vs 계약됨=숨김(2)"의 2원적 구조**다. 시드는 status 0·3(공개) 여러 건 + status 2(계약됨=숨김) 최소 1건으로 이 구조를 그대로 반영할 계획이다.
- `Schedule`(투어, `:189-231`): `unitId`(Int, 관계 선언 없는 평범한 FK — DB 레벨 외래키 제약은 마이그레이션 파일로 별도 확인 필요하나 Prisma 관계가 없어 최소한 ORM 레벨 강제는 없음), `status`(0 신청/1 대기/2 확정/3 취소, 기본 0).
- `LeaseContract`(계약, `:835-867`): `unitId`(필수, 실제 FK), `startDate`/`endDate`/`monthlyRent` 필수, `landlordId`/`tenantId`는 nullable이지만 시드에서는 실제 오너/세입자 User로 채울 계획, `status`는 `ContractStatus` enum(기본 `ACTIVE`).
- `CareServiceRequest`(케어 요청, `:892-923`): `contractId`(필수, `LeaseContract` 실제 FK) → **케어 요청을 만들려면 먼저 계약을 만들어야 한다.** `serviceType`은 `CareServiceType`(AIRCON/CLEANING/REPAIR/HANDYMAN), `preferredDate` 필수, `status`는 `CareStatus`(기본 `PENDING`).
- 시드 순서(의존성 때문에 고정): User(전 종류) → Unit(adminId/agentId를 세운 User id로) → LeaseContract(unitId + landlordId/tenantId) → CareServiceRequest(contractId) 및 Schedule(unitId) → 끝.

### AC-1/2/3/6 실행 결과 (2026-11-12, 대표가 `.env.local`을 로컬 주소로 바꾼 뒤)

- `npm run db:local:reset` 1차 시도에서 `db push` 단계가 `Error: P1017: Server has closed the connection.`로 실패 — 컨테이너 healthcheck가 "Healthy"를 보고한 직후라도 MySQL이 초기화를 마치지 않아 연결이 끊긴 것으로 보인다(최초 기동 시 1~2차 재시작이 있는 MySQL 공식 이미지의 알려진 동작). 몇 초 뒤 `npm run db:local:schema`만 다시 실행하니 바로 성공했다. 재현되면 `db:local:reset`의 healthcheck 대기를 더 길게 주는 개선이 필요할 수 있음(이번 범위에서는 고치지 않고 기록만 함).
- **AC-1**: `npm run db:local:schema` → `Your database is now in sync with your Prisma schema. Done in 10.02s`. `prisma/migrations/`는 전혀 수정하지 않았고 `--accept-data-loss`/`--force-reset`도 쓰지 않았다.
- **AC-2**: `npm run db:local:seed` → `시드 완료: 사용자 8명, 매물 30건, 투어 1건, 케어 1건, 계약 1건.` 로컬 DB(`localhost:3307`)에 직접 접속해 조회:
  - `users: 8`, level 목록 `[0,1,2,3,4,5,20,30]` (요구한 "0,1,2또는3,20또는30 각 1명 이상" 충족, 추가로 4/5도 포함).
  - `units: 30`, status별 `{0:6, 1:6, 2:6, 3:6, 4:6}` — 0(공개)/2(계약됨)/4(비활성화) 모두 포함.
  - `schedules: 1`, `careServiceRequest: 1`, `leaseContract: 1`.
- **AC-3**: `npm run db:local:seed`를 다시 실행 → 로그는 동일(`사용자 8명, 매물 30건, 투어 1건, 케어 1건, 계약 1건`), 재조회해도 `users:8, units:30, schedules:1, care:1, leases:1`로 **그대로**(증가 없음).
- **AC-6**: `npm run dev:local` 백그라운드 기동 후 `curl -s -o /dev/null -w "%{http_code}" http://localhost:3000/list` → `200`. `/list` 페이지는 SSR 쉘 안에 Suspense 스피너만 내려주고 실제 매물 목록은 클라이언트에서 `/api/units`를 호출해서 채우는 구조라, 그 API를 직접 curl로 확인: 응답 JSON에 `"title":"[RBS_LOCAL_SEED] Local Sample Unit 29"`, `"admin":{"email":"admin@example.invalid",...}` 등 시드 데이터가 그대로 보임. 로컬 DB만 조회했고 운영 DB는 건드리지 않았다(`DATABASE_URL`이 가드를 통과한 로컬 값으로 고정된 상태에서 실행).
- 로컬 MySQL 컨테이너와 `dev:local` 서버는 보고 작성 시점까지 계속 떠 있는 상태로 남겨뒀다(필요하면 `docker compose down -v`와 서버 프로세스 종료는 직접 정리 부탁).
