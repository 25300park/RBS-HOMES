## 2. 범위 안 (할 것)

진행은 두 단계다. **1단계가 끝나면 멈추고 대표 승인을 기다린다.** 승인 없이 2단계로 넘어가지 않는다.

**1단계: 읽기 전용 조사와 계획**
- `CLAUDE.md` 24번째 줄 부근에 비밀값 실제 값이 있는지 확인한다. **값은 출력하지 않는다.** 줄 번호와 "실제 값 있음/없음"만 보고한다.
- 아래 파일의 `RBS_SYNC_SECRET` 관련 줄이 (가) 이름만 있음 (나) 명백한 가짜 예시값 (다) 실제 값으로 의심됨 중 무엇인지 판정한다. 파일마다 줄 번호와 판정만 쓴다.
  - `.env.example`, `local.env.example`, `test-env.js`, `.github/workflows/ci.yml`, `prisma/seed-local.js`
  - `docs/env-vars.md`, `docs/briefs/B-20261111-04-env-cleanup.md`, `docs/screen-design/01-information-architecture.md`, `project_tree.txt`
- 추적되는 파일 전체(`git ls-files` 기준)에서 같은 종류의 비밀값이 직접 적혀 있는지 패턴으로 검색한다 (`NEXTAUTH_SECRET`, `RBS_SYNC_SECRET`, DB 연결 문자열의 비밀번호 부분, API 키 형태). 결과는 **파일, 줄 번호, 종류만** 보고한다. 값이나 값의 일부는 쓰지 않는다.
- `test-env.js`가 무엇을 하는 파일인지(환경변수를 출력하는지), 유지할지 삭제할지 제안한다.
- 2단계 수정 계획(파일별 변경 예정, 위험, 되돌리는 방법)을 보고한다.

**2단계: 대표 승인 후 수정**
- 실제 값을 이름만 남기고 자리표시자(예: `<set-in-env>`)로 바꾼다. 설명 문장은 유지한다.
- 실제 값처럼 보이는 예시는 명백한 가짜 값(예: `change-me`)으로 바꾼다.
- `CLAUDE.md`에 "비밀값은 이 파일에 쓰지 않는다" 한 줄을 추가한다.
- 1단계에서 승인된 `test-env.js` 처리(유지 또는 삭제)를 따른다.

## 3. 범위 밖 (하지 말 것)

- 이 브리프에 없는 파일, 화면, 테이블은 고치지 않는다.
- **옛 비밀값을 보고서, PR 설명, 브리프, 커밋 메시지, 로그에 쓰지 않는다.** 앞 몇 글자도 쓰지 않는다. 값 대신 "줄 N에 실제 값 있음"처럼 쓴다.
- `.env*` 파일을 읽거나 수정하지 않는다. 운영 DB에 접속하지 않는다. 배포하지 않는다.
- git 히스토리를 다시 쓰지 않는다 (force push, BFG 등 금지). 값은 이미 교체되어 무효다.
- 비밀값을 교체하지 않는다 (대표가 완료했다).
- 코드 동작을 바꾸지 않는다. 환경변수 이름을 바꾸지 않는다.
- CI 설정(`ci.yml`)은 값이 가짜이면 수정하지 않는다. 비밀 검사 단계 추가는 1단계 보고에서 제안만 한다.
- admin-rbs-homes 저장소와 대표의 로컬 파일(`03. env 파일` 폴더 등)은 건드리지 않는다.
