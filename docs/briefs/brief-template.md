# 브리프: <ID> <제목>

> 이 파일을 복사해서 `docs/briefs/<ID>-<slug>.md`로 저장하고 채운다.
> 에이전트는 작업 전에 이 파일을 읽고, 완료 후 10번(완료 보고)을 채운다.
> 11번(승인 기록)은 사람만 채운다.

- **ID**: B-YYYYMMDD-NN (예: B-20261020-01)
- **승인 등급**: 1 / 2 / 3 (`docs/approval-policy.md` 기준. 불확실하면 한 단계 위로)
- **PRD 근거**: PRD v1.0의 섹션 이름
- **저장소**: rbs-homes / admin-rbs-homes
- **브랜치**: `feat/<ID>-<slug>`
- **상태**: 초안 / 승인됨 / 구현 중 / 검증 중 / 완료 / 반려
- **작성**: 날짜, 작성자(사람 또는 AI)

---

## 1. 목표

한 문장으로 쓴다. "누가 무엇을 할 수 있게 된다" 형식을 쓴다.

예: 외부 브로커가 매물관리 대시보드에서 확인 요청에 매물별로 응답할 수 있다.

## 3. 범위 밖 (하지 말 것)

범위 밖을 적지 않으면 에이전트가 범위를 넓힌다. 반드시 적는다.

- 이 브리프에 없는 파일, 화면, 테이블은 고치지 않는다.

## 4. 영향받는 곳

| 항목 | 내용 |
| --- | --- |
| 화면과 라우트 | |
| DB (테이블, 마이그레이션 여부) | |
| 환경변수 (새로 필요한 것) | |
| 외부 연동 (이메일, 푸시, AI, 카카오) | |
| 개인정보 처리 (읽거나 저장하거나 전달하는 개인정보) | |

DB 스키마, 환경변수, 발송, 개인정보 중 하나라도 해당하면 3등급이다.

## 5. 사전 조사 (읽기 전용)

필요하면 에이전트가 먼저 조사하고 결과를 여기에 기록한다. 코드와 DB는 수정하지 않는다.
필요 없으면 "없음"이라고 쓴다.

## 6. 수용 기준

기계나 사람이 통과 여부를 판단할 수 있게 쓴다. 항목마다 확인 방법과 기대 결과를 적는다.

- [ ] AC-1: (확인 방법) → (기대 결과)
- [ ] AC-2:

**나쁜 예**: 검색이 빨라야 한다.
**좋은 예**: 로컬 시드 데이터에서 `GET /api/units/search`가 5회 평균 1초 이내이고, 기존 필터 조합 3개의 결과가 변경 전과 같다.

**나쁜 예**: 숨김 매물이 보이면 안 된다.
**좋은 예**: status가 4(숨김)나 2(계약됨)인 매물은 공개 검색 결과에 0건이다. 이를 확인하는 테스트가 있다.

- 추가하거나 수정할 테스트:

- 테스트를 지우거나 건너뛰어서 통과시키지 않는다.

## 8. 등급 판정 근거

왜 이 등급인지 한 줄로 쓴다. 3등급이면 해당하는 항목(스키마, 인증, 발송, 개인정보, 환경변수, AI 구조, admin)을 적는다.

## 9. 롤백

이 변경을 되돌리는 방법을 쓴다.

- 코드: 릴리스 태그나 PR 되돌리기로 충분한가?
- DB: 마이그레이션이 있으면 되돌리는 방법 (가능하면 기존 데이터에 영향 없는 추가 변경만 한다)
- 발송: 발송 스위치(`EMAIL_MODE`)로 끌 수 있는가?
